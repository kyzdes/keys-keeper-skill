**Независимое архитектурное ревью Keys Keeper — 2 октября 2026**

Проверенная версия: `96671fd73ca42503b5fa57da775aec3cc5b0d1c6`, ветка `codex/simplify-and-harden`, кандидат 0.12.0. Выводы относятся к этому commit, а не к опубликованному 0.11.1 или любой будущей версии.

Архитектура стала компактнее: удаление S3/WebVault, общий путь мутаций, единая подготовка снимков и ограничение ресурсов VPS — правильные изменения. Однако кандидат пока нельзя считать завершённым: воспроизведены ошибки сохранения отзывов устройств, конкурентной ротации секрета, идентичности ссылок и восстановления optional secret. Основная проблема теперь — согласованность состояния между несколькими успешными операциями, а не количество файлов или отсутствие ещё одного слоя абстракций.

В ревью участвовали три субагента: два новых критика по VPS и секретам/восстановлению и перекрёстный ревьюер установки, архитектуры и инструкций. Перекрёстный ревьюер ранее работал над удалением S3/UI; проверка его собственной работы не выдаётся за независимую. Ведущий ревьюер прочитал затронутые реализации и самостоятельно повторил все шесть существенных findings ниже. Для гонки секрета дополнительно проверен реальный обработчик API ротации. Низкоприоритетная несогласованность audit проверена отдельным вызовом общего helper.

Предыдущий отчёт о реализации использован как описание обещанных контрактов. Его выводы и зелёный CI не использованы как доказательство корректности этих контрактов. Пробы использовали синтетические хранилища и backend в памяти; VPS-пробы — тестовый relay с настоящими подписями. Настоящие vault, Keychain, VPS, установленные приложения и marketplace не изменялись. Это ограниченное ревью кода и сценариев состояния, не полный криптографический аудит или нагрузочный тест production.

**R1. Root не сохраняет подписанный им отзыв независимо от ответа сервера.**

Код: `src/keys_keeper/cli_sync_vps.py:651–677`; проверка сохранённого evidence — `src/keys_keeper/sync_vps.py:581–589`.

`cmd_vps_revoke` проверяет HEAD, создаёт и подписывает statement, отправляет его relay, затем вызывает `refresh_trust_anchor()` без требования увидеть именно отправленный отзыв. Refresh сохраняет только то, что снова вернул relay.

Воспроизведение: на непустой корректной цепочке root отзывает peer; тестовый relay подтверждает запрос, но продолжает отдавать peer как active. Исходящий statement проверен настоящим root public key. CLI возвращает 0 и сообщение об успехе; локально остаётся `revocations: {}`. После этого peer подписывает следующий commit, и тот же root принимает его через обычный `pull()`.

Это отличается от невозможности сообщить об отзыве компьютеру, который никогда о нём не знал: root только что сам создал доказательство отзыва. Условия последующего обхода — недобросовестный relay и доступ к ключу отозванного устройства. При честном relay описанного сокрытия нет.

Минимальное исправление: сохранять точное локально подписанное evidence с проверенным cutoff в существующем trust state, проверять его наличие/равенство при подтверждении сервера и явно различать локальный запрет, публикацию запроса и подтверждение relay. Повторный запрос без expected evidence недостаточен. При неопределённом сетевом исходе состояние должно оставаться восстанавливаемым; сообщение об успехе не должно подменять доказательство.

Проверка исправления: ACK без соответствующего evidence не завершает отзыв подтверждённым успехом; последующий commit этого signer после cutoff отклоняется, в том числе после перезапуска клиента. Уверенность высокая, сценарий повторён ведущим ревьюером.

**R2. Trust state не сохраняет монотонность знания об отзывах.**

Код: `src/keys_keeper/sync_vps.py:444–466`, `867–871`, `945–948`; пустой `push()` также выходит без сохранения состояния в `979–980`.

Сценарий A: операция A проверила цепочку до отзыва. Операция B при том же HEAD проверила новый подписанный отзыв и записала его. A заканчивает `pull()`, читает уже обновлённый файл B, проверяет только commit anchor и заменяет файл своим старым набором отзывов. Проверка идентичности файла не помогает: A прочитала `previous` уже после B, поэтому файловая замена формально корректна. Воспроизведено `revocations: {}` после подтверждённой записи B, а затем принятие нового commit от ранее отозванного peer при сокрытии отзыва relay.

Сценарий B: при пустой истории корректный отзыв с checkpoint 0 проверяется, но `refresh_trust_anchor()` не записывает ничего, поскольку `verified is None`. После сокрытия отзыва следующий genesis от этого peer принимается. Этот сценарий не требует параллельных операций.

Контрольные пробы показали: нормально сохранённый отзыв обнаруживает и сокрытие, и замену другим правильно подписанным statement. Значит, проблема в долговечности evidence, а не в отключённых проверках подписей или отсутствии свежего запроса.

Минимальное исправление: сохранять trust state с необязательным commit anchor и обязательным монотонным набором известных отзывов. Обновление должно проверять все компоненты trust state. Для общего device ID разрешено только идентичное evidence; отличающийся подписанный cutoff — конфликт, а не повод выбрать больший sequence. Если при сохранении обнаружен ранее неизвестный этому proof отзыв, для более нового HEAD надо перепроверить авторов цепочки относительно cutoff либо повторить proof. Простое объединение словарей без этой проверки недостаточно.

Проверка исправления: межоперационное чередование при одном HEAD, отзыв до genesis, restart, конфликт evidence и новый HEAD после cutoff. Уверенность высокая, оба сценария и отрицательные контроли повторены ведущим ревьюером.

**R3. Ревизия metadata не покрывает все изменения секрета.**

Код: `src/keys_keeper/models.py:232–233`, `src/keys_keeper/master_journal.py:186–202`, `248–255`; применение — `src/keys_keeper/sync_vps.py:874–938`; реальная ротация API — `src/keys_keeper/api.py:853–860`.

В schema 2 ревизия зависит от metadata, timestamp имеет точность одну секунду, а `content_revision` меняется только при наличии schema-3 catalog. Две ротации в одну секунду могут оставлять byte-identical metadata. Проверка `expected_revision` при применении снимка тогда не обнаруживает конкурентное изменение секрета.

Воспроизведение: подготовлен локальный снимок со значением A; remote содержит B, которое выигрывает сравнение с A. Затем обработчик API успешно заменяет секрет на C и возвращает `committed: true`, сохраняя timestamp той же секунды. Старый подготовленный merge проходит CAS и записывает B поверх C. В пробе C специально выбран так, что при повторном чтении именно C выиграл бы сравнение с B. Это потеря конкурентной записи, а не обычный допустимый исход deterministic merge.

Минимальное исправление: optimistic-concurrency token должен меняться при каждой мутации содержимого, включая secret-only write и удаление optional secret в schema 2. Варианты в существующей архитектуре — journal-backed generation или повторная проверка полного подготовленного состояния под общей границей мутации. Повышение точности timestamp само по себе не даёт строгой гарантии. Нельзя просто навязать schema 3: legacy snapshot apply для неё намеренно запрещён.

Проверка исправления: фиксированные часы; API rotation между snapshot preparation и apply; старый apply должен получить `ConcurrentMutation` и пересчитать merge. Добавить отдельные случаи secret и passphrase. Уверенность высокая; исходная проба и вариант с реальным API handler повторены ведущим ревьюером.

**R4. Защита ссылок по имени не выдерживает несколько синхронизаций.**

Код: `src/keys_keeper/vault_snapshot.py:278–296`; потребитель ссылки — `src/keys_keeper/ssh_runner.py:91–97`; разрешение ссылок — `src/keys_keeper/refs.py`.

Текущая защита запрещает переназначение только когда и исходный, и итоговый target найдены в одном merge. Отсутствующий target теряет связь с прежним ID.

Воспроизведение: устройства A и B знают ключ `prod-key` с ID X. A добавляет сервер со ссылкой на это имя, а B, ещё не получивший сервер, удаляет ключ. После обмена на A остаётся сервер с висячей ссылкой. Затем B создаёт новый ключ с тем же именем, но ID Y. После следующего обмена исходная ссылка сервера разрешается в Y. Все публикации и подписи валидны; злонамеренный relay не нужен. Сценарий выполнен через настоящие `push()`/`pull()` на тестовом relay.

Последствие — выбор другого credential без явного изменения ссылки. В SSH это означает использование другого ключа; ревью не утверждает, что такой вход обязательно успешно выполнится.

Минимальное исправление без нового wire protocol: отклонять merge, который превращает ранее связанную ссылку сохраняющейся записи в висячую, и требовать явного разрешения конфликта. Не выполнять молчаливый cascade: разрешение на удаление зависимостей отсутствовало. Устойчивые ссылки по ID — возможное отдельное развитие модели, но миграция ради срочного исправления не обязательна. Нужна также явная политика для уже существующих висячих ссылок.

Проверка исправления: последовательность create reference → remote deletion → sync → name reuse → sync; проверять ID target после каждого шага, а не только отсутствие дублей имён. Уверенность высокая, повторено ведущим ревьюером.

**R5. `None` одновременно означает «не менять» и «значение отсутствует».**

Код: `src/keys_keeper/service.py:43–46`, `src/keys_keeper/master_journal.py:463–474`, `src/keys_keeper/cli.py:1073–1083`.

`SecretInput` с `passphrase=None` при обычном update означает отсутствие записи в наборе изменений. Импорт же получает `None` из полного backup, где оно означает отсутствие optional passphrase. Эти два контракта смешаны.

Воспроизведение: существующий SSH entry имеет secret и passphrase; backup для той же записи содержит новое значение secret и `_secret_passphrase: null`. `keys import ... --replace` возвращает 0 и `imported 1 entries`. Следующий snapshot по-прежнему содержит старую passphrase. Таким образом, замещённая запись не соответствует backup, хотя команда сообщает успех.

Минимальное исправление: явно различать «не менять», «удалить» и «записать значение» внутри существующего mutation pipeline. Для полного replacement передавать account deletion через тот же журнал, что и запись секрета; не удалять passphrase отдельной незащищённой операцией после импорта. Не следует глобально менять смысл `None` для всех edit-команд.

Проверка исправления: present → absent, absent → present, empty string → absent; не только импорт в пустое хранилище. Уверенность высокая, реальный CLI import с синтетическим контекстом повторён ведущим ревьюером.

**R6. Инструкция для агента обещает неверные эффекты диагностической команды.**

Код: `src/keys_keeper/agent_rules/canonical.py:269–280`; `src/keys_keeper/personal_sync.py:157–169`.

Таблица скилла говорит, что `keys devices status` не читает секреты, не обращается в сеть и не требует approval. В настроенном master вызов открывает encrypted state и читает `kk:project-runtime-key`. При отказе backend команда завершается с кодом 1. Чтение root unlock material подтверждено на свежем runtime; отсутствие сетевого запроса также подтверждено.

Это не вывод пользовательского секрета в stdout и не доказательство появления нативного диалога Keychain. Проблема — ложная гарантия credential-free операции: агент может выбрать её, когда пользователь разрешил только диагностику без доступа к секретам.

Минимальное исправление: честно указать чтение локального unlock material, сохранив функциональность команды, и перегенерировать производные инструкции. Если действительно нужен credential-free статус, сначала определить отдельный узкий публичный результат; не дублировать всю расшифрованную модель в открытом кеше ради таблицы.

Проверка исправления: effects contract для configured/unconfigured master, replica, холодного runtime и отказа backend. Уверенность высокая, CLI-проба повторена ведущим ревьюером.

**R7. Сообщение о commit и audit расходятся.**

Код: `src/keys_keeper/api.py:176–188`; контрастирующий контракт CLI закреплён в `tests/test_cli_adapter_outcomes.py:98–102`.

`_operation_failed(..., committed=True)` возвращает подтверждение публикации изменения, но безусловно записывает `success=False`, `error="operation failed"` в audit. Отдельная probe helper дала одновременно `api_committed=true` и `audit_success=false`. Это проверка существующей ветки контракта, а не доказательство частоты такого сбоя в рабочем vault.

Минимальное исправление: разделить факт side effect и полноту подтверждения операции в общей модели результата, одинаково применяемой CLI/HTTP/audit. Не превращать неизвестный commit в успех. Для известного commit audit не должен выглядеть как доказательство отсутствия изменения.

Уверенность высокая в несогласованности helper; влияние ограничено отчётностью при ошибке после публикации. Предположение, что промежуточная ошибка записи journal автоматически выдаёт весь user mutation за committed, не подтвердилось: соответствующие слои преобразуют её в собственные ошибки.

**Что следует сохранить в архитектуре.**

Общий путь `VaultService → MasterMutationManager → OperationJournal` существенно полезнее отдельных rollback-обработчиков в CLI и API. Подготовка metadata до внешнего side effect, сохранение before/after images и блокировка проекций при pending операции создают основу для восстановления после падения. Найденные R3/R5 требуют уточнения контракта состояния, а не ещё одного менеджера транзакций.

`vault_snapshot` объединяет полную подготовку backup и KK2 снимка. Required secret нельзя молча пропустить; отсутствующая optional passphrase отличается от ошибки чтения; размер снимка ограничен. Удаление S3/WebVault убрало отдельный transport, web-приложение и background hook без замены их новой инфраструктурой.

`private_files`/`secure_io` дают общее место для ограниченного чтения, проверки файлов и публикации. Это важные границы, которые нельзя удалять ради уменьшения количества модулей. Ревью не повторяло все платформенные DACL-тесты.

VPS продолжает проверять membership, revocation signatures, cutoff и signed ancestry при каждом обращении. Пагинация и получение только текущего ciphertext сокращают работу без намеренного отказа от проверок. R1/R2 локализованы в сохранении доказательств между операциями.

Relay quota counters обновляются триггерами в той же SQLite-транзакции, что и данные. Проверка scope/global budget не сканирует историю. Control reserve, ограничения соединений и активных обработчиков, абсолютный deadline чтения запроса и фиксированная обработка SQLite BUSY — хорошие решения для небольшого VPS. Квоты логических данных не заменяют ограничения физического диска и RSS.

Backend создаётся лениво после проверки роли профиля. Есть один canonical источник скилла, проверки generated/installed artifact, read-only режим проверки marketplace pin и явная политика fallback updater. Эти механизмы стоит сохранять, добавив проверку фактических эффектов команд.

**Как сократить систему без удаления нужной функциональности.**

| Изменение | Зачем | Ограничение |
| --- | --- | --- |
| Сделать один локальный контракт trust state: optional anchor + known revocations + checked update | Закрывает R1/R2 и убирает зависимость знания об отзыве от наличия snapshot | Без нового сетевого протокола; conflict/cutoff остаются строгими |
| Довести общий mutation contract до полной ревизии содержимого и явных account operations | Закрывает R3/R5 вместо новых специальных веток в sync/import | Не смешивать patch и replacement |
| Убрать принятие решений по подстроке `explicit schema-v3 migration` в CLI и snapshot preflight | Сейчас текст исключения служит скрытым API между слоями | Достаточно одного типизированного запроса schema/capability, без framework |
| Унифицировать outcome mapping для CLI, HTTP и audit | Убирает R7 и повторение `committed`/`audit_status` условий | Не объединять successful, failed и unknown в boolean |
| Оставить `ProjectRuntime` местом композиции, постепенно вынести операции recovery/enrollment в существующие application-модули | Сейчас он объединяет выбор профиля, кеши, backup, recovery, enrollment и sync | Выносить при работе над конкретным сценарием, не переписывать весь runtime сразу |
| Свести повторяемые operational defaults к одному проверяемому источнику | Уже есть дрейф docs: operations guide обещает 4 handler, код задаёт 2 | Проверять контракт, не копировать ещё одну таблицу вручную |

Не рекомендую сейчас удалять KK1, KK2 или KK3 под видом чистки дубликатов. KK1 — переносимый backup; KK2 — full-vault multi-writer sync; KK3 — master/project/personal delivery с иной моделью прав. Объединять их подписываемые payload, recovery и grant semantics опаснее, чем оставить небольшой объём специализированного кода. Вывод KK2 из эксплуатации возможен только отдельной задачей с инвентаризацией пользователей, миграцией и проверкой восстановления.

Не стоит удалять `SecretInput`, `DeleteResult`, типы trust/protocol errors, `AccessContext`, профильные роли или sidecar/journal state только потому, что они малы. Эти модели выражают существенные различия. У `SecretInput` нужен более точный смысл, а не удаление. Нет подтверждённого списка дополнительных entry types, которые можно убрать без потери функциональности; name-based references — конкретная проблема, но удаление server/SSH модели её не решает.

**Известные ограничения и рекомендации, которые не выданы за новые runtime-баги.**

1. История конечна: KK2 имеет предел 10 000 commits и не позволяет обычному клиенту опубликовать 10 001-й; KK3 ограничивает обход цепочек. Автоматического безопасного удаления истории нет. Нужен понятный путь capacity/checkpoint recovery, но нельзя освобождать место удалением доказательств отзыва или idempotency records.
2. Снижение одновременных активных запросов уменьшает peak memory за счёт отказов/повторов при перегрузке. Это не доказательство увеличения throughput. Новое production-измерение CPU/RSS/p95 в этом ревью не выполнялось.
3. `docs/PROJECT-RELAY-OPERATIONS.md:158–161` отстаёт от реализации: указаны четыре handler и только socket inactivity timeout, тогда как код задаёт два активных запроса и использует absolute input deadline. Общие ограничения reverse proxy по-прежнему полезны, но фактический контракт следует описывать точно.
4. Generated onboarding подставляет версию runtime в `git@v0.12.0`; remote tag отсутствовал при проверке ревьюером (`git ls-remote`, exit 2). README честно обозначает unreleased candidate. Это release gate, а не доказательство поломанного опубликованного marketplace: перед распространением нужен доступный immutable ref или явный verified-wheel flow для кандидата. Установки не выполнялись.
5. Устройство с ранее полученным KK2 VaultKey сохраняет старые секреты после revoke; клиент без независимого witness не может выявить всякий согласованный split view relay. Это отдельные ограничения модели, не оправдание R1/R2, где клиент уже знает об отзыве.

**Порядок исправлений и проверок.**

Сначала R1/R2 одним небольшим изменением trust-state lifecycle, сохранив отдельные регрессии для ACK omission, same-HEAD race и empty HEAD. Затем R3 — полноценная локальная ревизия для secret mutation. После этого R4 — запрет неявной потери/перепривязки identity; R5 — replacement account semantics в существующем journal. R6 и R7 исправлять отдельно: они затрагивают инструкции и отчётность, а не формат синхронизации.

Основной пробел тестов — последовательности, а не количество assert. Нужны контролируемые interleavings, фиксированные часы, рестарт между стадиями и цепочки из нескольких корректных операций. Обычные тесты «одна операция завершилась успешно» не обнаруживают rollback revocation или исчезновение identity между двумя merge. Для модели секретов полезна одна общая матрица absent / empty / value / unchanged / denied / failed across snapshot, import и sync.
