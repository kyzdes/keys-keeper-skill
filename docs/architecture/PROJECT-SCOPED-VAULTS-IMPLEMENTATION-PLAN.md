# План реализации папок, проектов и ограниченной синхронизации

Дата: 2026-09-05. Статус: **план подготовлен; локальный прототип частично реализован**.
Продуктовая интеграция, выпуск и production verification не завершены.
Основа: [архитектура](PROJECT-SCOPED-VAULTS.md); исходный анализ `c3ab31f`,
текущая рабочая ветка `codex/project-scoped-vaults` поверх `223a677`.
Незакоммиченный прототип — материал для проверки решений, не готовый релиз.
Рабочие ключи не мигрировались, проектная выдача на рабочие машины не включалась.
Это отдельная продуктовая работа; ограничения behavior-preserving refactor
из `INTERNAL-REFACTOR-PLAN.md` не запрещают необходимые здесь изменения схемы.

План проверен тремя сабагентами: **Astra** — протокол и угрозы;
**Sol** — профили, устойчивое хранение и восстановление;
**Terra** — каталог, пользовательские сценарии и интеграционные проверки.
Результаты сведены в зависимости, критерии приёмки и обязательные доработки ниже.
Review автора собственного протокола не считается независимым криптоаудитом.

## 1. Результат первой версии

- Мастер хранит полный каталог, папки, проекты и управляет доступом.
- На рабочей машине доступны только назначенные ей проектные наборы.
- Машина может создавать новые записи своего проекта. Они автоматически
  появляются на мастере после проверки и затем у получателей этого проекта.
- Машина не меняет существующие записи, даже ранее созданные ею.
- Один оригинал ключа на мастере может быть явно включён в несколько проектов.
- Личные записи по умолчанию не выдаются. Папки и теги не изменяют разрешения.
- При выключенном мастере существующие ключи работают, новые ждут в защищённой
  очереди. Сбои и повторные запросы не приводят к потере или дублированию записей.

Рабочее обозначение `scope` означает проект и окружение, например `alice/dev`.
Для проекта без окружений используется один scope `default`.

Зафиксированные ограничения: один мастер-издатель; отдельный шифрованный снимок
на scope; полный снимок вместо delta/CRDT; права `reader` и `contributor=read+create`;
никакой автоматической выдачи по тегам и никаких прав на другие scopes через refs.
Динамические credentials, несколько мастеров и удалённое редактирование исключены.

## 2. Порядок поставки

Каждая строка — отдельный PR или небольшая последовательность PR с одним
условием приёмки. Имена новых файлов ниже предлагаемые; существующие пути проверены.
Чекбоксы обозначают приёмку полного требования, а не наличие отдельного файла.
Ни один пакет пока не принят целиком; состояние прототипа приведено в разделе 16.

Три контрольные точки поставки:

1. **Каталог:** после PR-02 допустим выпуск папок/проектов без сетевой выдачи,

2. **Закрытый пилот:** после PR-08 и минимального CLI — только синтетические ключи.
3. **Использование с рабочими ключами:** после PR-11; весь пользовательский цикл,
   проверка восстановления и противодействия обходу доступа должны пройти.

Новый режим не включать автоматически при обновлении установленного CLI.

| Исполнитель | Основная зона | Кто проверяет результат |

на каждый этап; сабагенты не меняют их одновременно.

## 6. PR-03 — устойчивые операции до сетевой записи

**Изменить:** `service.py`, `store.py`, safe I/O и локальную composition.
**Добавить:** `operation_journal.py`, `project_jobs.py`, recovery diagnostics.

Разделить три задачи; не переписывать все backend под одну новую БД:

1. **Публикация мастера.** Получать согласованные metadata и значения выбранных
   записей под общей mutation boundary. После освобождения lock работать с
   зашифрованным подготовленным снимком; не держать lock во время HTTP.
2. **Импорт только новых записей.** Устойчиво резервировать request ID и новый
   canonical UUID до записи backend. Entry, provenance, dedup record и намерение
   публикации фиксировать одной metadata-транзакцией после проверки секретов.
3. **Установка реплики.** Записать новое поколение только внутри replica-профиля,
   проверить его, затем атомарно переключить active generation. Сохранять предыдущее
   поколение до успешного переключения; GC не затрагивает соседний профиль/outbox.

- [ ] Журнал содержит стадии и необходимые данные для завершения или отката.
  Секретные before/after images, если нужны, хранятся только зашифрованными.
- [ ] Для изменений существующих master records сохранять original-item/ACL
  semantics. Добавить устойчивое намерение и recovery только для затронутых
  записей; незавершённую мутацию не разрешать публиковать.
  Стадии: `prepared` (encrypted before/after и affected accounts) →
  `backend_applied` → `metadata_committed` → `completed`. Проверять metadata-only,
  secret-only, rename и delete с зависимостями отдельными process-kill сценариями.
- [ ] После старта сначала восстанавливать незавершённые операции, затем sync/UI.
  Ошибка восстановления закрывает затронутую операцию с понятным статусом.
- [ ] Квитанция `accepted` создаётся только после устойчивой записи. Dedup record
  сохраняется и после удаления ключа: повтор старого create не воскресит его.
- [ ] Очередь публикаций выводить из desired/applied revisions. Потеря уведомления
  или сбой после secret update не оставляют обновление навсегда неопубликованным.
- [ ] Фиксировать порядок locks и запрещать взаимные вложенные захваты вразнобой.
  Подготовить снимок и зафиксировать immutable job под согласованной mutation
  boundary, затем освободить state/store/generation locks перед HTTP. После
  ответа отметить applied revision через CAS; более новая desired revision
  остаётся в очереди. Single-flight job coordination не должна удерживать
  блокировку пользовательского каталога во время сетевого ожидания.
- [ ] Отзыв сначала фиксировать в локальном зашифрованном журнале. Сохранённый
  запрет нельзя отменить отсутствием revocation в ответе relay; см. D01.

**Проверки:** новый `test_project_recovery`, реальные дочерние процессы с kill
после каждого устойчивого шага; повторный startup, disk-full, отказ backend,
два параллельных импортера и читатель во время смены generation. Одних mocked
exceptions недостаточно для проверки process death.

**Готово, когда:** после рестарта видна полная старая или полная новая версия,
нет успешной квитанции на потерянный ключ и нет дубля при повторной доставке.

## 14. Миграция, выпуск и откат

1. Проверить актуальную установку и inventory, резервную копию и restore. В этой
   задаче реальные ключи не инвентаризируются и не мигрируются.
2. Обновить relay до совместимой версии с новым API, сохраняя KK2. Проверить
   новую schema БД и восстановление backup на отдельной среде.
3. Обновить master и все его writers. Мигрировать metadata под lock;
   прежние записи остаются local_only, folder «Неразобранное».
4. Включить режим сначала для одного scope и одной чистой машины; явно выбрать
   состав, сверить fingerprint и проверить функциональную доставку.
5. Проверить create обратно на M, shared update, отзыв тестовой машины и restore.
   Затем подключать остальные scopes и устройства по одному.
6. Старый full-vault профиль не превращать в ограниченный скрытием записей.
   Если машина уже получала весь vault, зафиксировать прежний доступ и отдельный
   план ротации; новый режим не отменяет прошлых копий.

При ошибке до миграции — отключить новую функцию. После миграции — остановить
publish/import и использовать совместимую версию клиента либо восстановить
проверенную копию в отдельный профиль. Старый writer на новой schema запрещён.
При откате relay не удалять новые таблицы и непринятые submissions. Если старая
версия не умеет их обслуживать, заморозить новый API и сохранить очередь.

Безопасный откат сохраняет закрытый доступ: он никогда не включает обратно
отозванный grant, общий VaultKey или старую раздачу ради восстановления сервиса.
После любого restore требуется проверка актуальности политики, а не только `/healthz`.

regression evidence приведены в ADR и отчёте. Внешний криптоаудит и миграция
рабочих машин остаются отдельными этапами; внутренний review их не заменяет.

### D01. Локальный отзыв, независимый от relay — обязательно

Локальная запись `revocation_intent(scope, grant, generation, operation_id)`
устойчиво сохраняется **до HTTP**. Она немедленно запрещает приём ещё не принятых
create и подготовку новых публикаций с этим получателем. Список отозванных grants
монотонный: отсутствие записи в ответе relay ничего не отменяет.

Подготовленная публикация, включающая отзываемый grant, не отправляется повторно
после отзыва. Если она могла быть принята до потери ответа, считать её данные
потенциально раскрытыми, проверить её signed HEAD и завершить следующий epoch
без отозванного устройства. Нельзя очистить pending и незаметно потерять обновления.
Если relay не позволяет восстановить согласованную историю, сохранить
`recovery_required`, без публикации новых секретов со старым ключом.

**Проверка:** ложный HTTP-успех block, скрытый revocation, отказ backend и kill
между каждой стадией. После рестарта сохранены запрет и `rekey pending`.
Этот разрыв обнаружен в `ProjectMaster.revoke()` / `_verified_remote()` прототипа.

### D02. Подлинность, свежесть и установка — разные состояния

Для нового подключения выбрать challenge-response с мастером. Устройство
генерирует случайный одноразовый challenge; после выдачи grant мастер подписывает
ответ, связывающий challenge, invite, device public keys, scope, policy/epoch,
точный итоговый snapshot hash/sequence и срок действия. Устройство проверяет
pin мастера, собственный challenge и данные grant до установки.
Сервер может передать ответ, но не является источником его подлинности.

`trusted_checkpoint` — доверенный ориентир для проверки истории;
`applied_checkpoint` — уже установленное поколение. У новой машины второй пуст
до успешного переключения generation. Их нельзя хранить в одном поле с двумя
значениями смысла. Отставший клиент за пределом разрешённой догрузки истории
получает свежий ориентир через ту же процедуру, а не отключает проверку цепочки.

При выключенном мастере уже подключённая машина использует проверенную копию,
а UI показывает время последней подтверждённой проверки. Подпись старого снимка
не доказывает, что relay не скрывает более новый. Без доступного мастера или
независимого свидетеля полную защиту от замораживания HEAD не обещаем;
новое подключение/обновление доверенного ориентира ждёт мастера.

**Проверка:** повтор старого invite, challenge-ответа и корректно подписанного
старого HEAD не завершает новое подключение. Первый pull действительно устанавливает
данные; ограничения истории не обходятся автоматическим доверием relay.

### D03. Общие ключи и их реальные получатели

Для canonical entry вычислять объединение grants всех назначений. Экран
«Где используется» показывает scopes, устройства и состояния доставки; при
исключении из одного scope показывает оставшиеся пути доступа. Независимые
ключи шифрования не делают одно и то же значение credential разными секретами.
При компрометации учитывать права самого API/SSH credential у провайдера:
ограничение выдачи Keys Keeper не сужает эти внешние права.

Ротация внешнего credential создаёт одну новую master content revision и
задачу для каждого его scope. Общей сетевой транзакции нет: пользователь видит
частичную доставку. Если провайдер допускает одновременные старый/новый credentials,
обычный переход завершается после применения новой версии нужными получателями.
При компрометации немедленный отзыв у провайдера может прервать работу отставших
машин; восстановление доставки не должно снова включать скомпрометированный ключ.
Автоматизацию конкретных провайдеров первая версия не обещает.

**Проверка:** одно устройство имеет общий ключ через два scopes; отзыв одного
не отображается как полный отзыв credential. Сбой во втором scope сохраняет
незавершённый статус ротации и повтор именно недоставленной ревизии.

### D04. Ограничить весь объём работы, не только pending

До пилота конфигурация должна задавать: общий диск relay и на scope, число/размер
исторических снимков, число соединений и параллельных crypto/DB операций, timeout
чтения body, максимальный ответ, количество и совокупные байты догрузки истории.
Конкретные значения фиксировать по максимальному поддерживаемому снимку и
нагрузочной пробе PR-05; отсутствие лимита не является допустимым default.

Retained checkpoint должен позволять новое доверенное подключение по D02.
GC не удаляет pending, постоянный master dedup, запреты и high-watermark generations.
Квитанции можно архивировать по определённому протоколу восстановления, но старый
request не становится новым из-за удаления серверной строки. Обработку GC и
несовместимого restore проверять вместе. При исчерпании диска запретить новые
записи, сохранив корректный статус и возможность читать уже принятые данные.

**Проверка:** длительное накопление истории, несколько одновременных больших
запросов и flood одного scope сохраняют заданные бюджеты и доступность другого.

### D05. Независимая проверка криптографии до рабочего использования

Прототип использует X25519/HKDF/AES-GCM и Ed25519. Это собственная композиция,
не HPKE. ADR PR-00 должен выбрать поддерживаемую HPKE-реализацию либо обосновать
и независимо проверить текущий suite. Wire profile до этого не объявляется
стабильным. Самогенерируемый fixture не заменяет независимые векторы.

Даже выбор HPKE не устраняет replay, epochs и checkpoint: эти задачи остаются
у протокола приложения; см. [RFC 9180, раздел 9.7](https://www.rfc-editor.org/rfc/rfc9180.html#section-9.7).
Проверку прав на каждом пути API включить отдельно, согласно
[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request).

**Проверка:** другой автор воспроизводит байтовый контракт и негативные векторы;
все findings, влияющие на выдачу/расшифровку/подпись, закрыты до рабочего пилота.

### D06. Восстановление не создаёт второго мастера

Backup фиксирует согласованную ревизию каталога/секретов, dedup, journals,
authority/inbox/scope keys, policies, spent grants и trusted/applied checkpoints.
Копирование только JSON-каталога или только служебного state недостаточно.
Все секретные компоненты шифруются; restore проверяется в отдельной среде.

Восстановленный профиль сначала запускается в режиме recovery без publish/import.
Продолжение прежней идентичности допускается только после подтверждения актуальной
истории и вывода прежнего издателя из работы. CAS relay не доказывает, что двух
писателей нет: недоверенный сервер может показывать им разные ветви.

Если актуальность или прекращение работы старого мастера нельзя подтвердить,
обязательный путь MVP — новая управляющая идентичность, новые scopes/epochs и
явное переподключение получателей с новым pin. Старые полномочия автоматически
не наследуются. Это восстанавливает управление новой системой, но не стирает
копии у прежних устройств; внешние credentials при необходимости отзываются отдельно.

**Проверка:** stale backup, отсутствующий принятый request в dedup и одновременный
запуск прежнего мастера не приводят к автоматической записи/раздвоению истории.
При отсутствии достоверного состояния результат — `recovery_required`, затем
проверенный takeover или новое подключение; не молчаливое принятие данных relay.
